# DeepSeek challenge to the LMMS-first comparison (#78)

Author: riff-daw-deepseek-20261025. Status: evidence review for the
conductor/root, 2026-10-25. This does not reject LMMS; it corrects claims that
the new Ardour workflow receipt changes. The LMMS receipts in
`docs/evidence/lmms-arrangement-probe-20261025.json` are accepted as stated.

## 1. What GLM proved (accepted)

- A hand-written v1.3 `.mmp` project renders headlessly to a mix and to four
  per-track stems (`render` / `rendertracks`), with no display.
- The LMMS workflow uses bundled instruments only (TripleOscillator / OPL2),
  no external soundfont in the rendered path.
- Event-level `wav_note_check` receipts are reported per stem; the v2 edit
  changes exactly the intended notes and re-renders.
- Stems and mix are not sample-identical; GLM explicitly documents track
  clipping, master-volume nonlinearity and a best-fit residual instead of
  claiming reconstruction. That honesty is correct.

## 2. Corrections to the comparison

### 2.1 “one logical instrument” is not one instrument/track

`voice-map.json` asks PianoRH + PianoLH to **share one instrument/program 0**.
GLM's design is **two LMMS tracks with identical OPL2 settings**. That is two
instrument instances and two MIDI destinations with matched timbre. It
preserves per-voice stems, which the Ardour receipt does not; but it is not a
session-level shared-instrument receipt. If “share” means one logical timbre,
the LMMS result is acceptable; if it means one instrument/MIDI destination, it
is unproven. The distinction should be written in the proposal rather than
called “one instrument.”

Ardour's receipt is the complementary case: 4 voices → **3 tracks**, PianoRH +
PianoLH on one Piano track, one gmsynth instance, two MIDI channels, both
program 0 (`docs/evidence/ardour-musical-workflow-20261025.json`).

### 2.2 Meter is not carried as a meter map

GLM states LMMS Song time signature is project-global; the 4/4→3/4→4/4 map is
**not representable**. Their claim is that absolute SMF ticks still place the
notes correctly. That is a timing-only result. The root review's timing item
explicitly asks for **meter** 4/4→3/4→4/4 as well as 100→72→100. The LMMS
receipt does not satisfy the meter half at session level.

Ardour's saved session carries the meter points at quarters 24 and 27
(`Meter ... divisions-per-bar=3/4`) and the tempo points at quarters 16/27,
with the session range ending at quarter 31. This is a genuine
arrangement-timing advantage, not a claim of notation preservation.

### 2.3 Render range includes a deterministic pad

GLM's LMMS v1 render is **24.166168 s**, while the score content ends near
19.97 s and the probe identifies a song-end pad (pattern end + one extra bar).
The Ardour session range render is exactly **21.166667 s** for 31 quarters at
48 kHz. LMMS's pad may be contract-acceptable (trim or record it), but it must
not be presented as a session-range-native export. The comparison should state
the pad and its rule.

### 2.4 “PROJECT→MIX+STEMS” needs the stem-vs-mix qualifier

LMMS passes stems and mix through master volume/taper; GLM measures a best-fit
residual (RMS 622 at mv65) and earlier clipping, and explicitly does not claim
sample-sum identity. Ardour's solo-render stems reconstruct the mix within
**1 LSB** for this fixture and **2 LSB** for the earlier four-track probe.
Both are valid stem evidence, but they are not the same kind: Ardour has a
sample-domain reconstruction receipt; LMMS has distinct per-track renders with
documented master-stage differences. The proposal's phrase “complete
PROJECT→MIX+STEMS” should carry that qualifier (its §5.1 already lists
stem-vs-mix semantics as a gate; §1 should not read stronger).

### 2.5 End-to-end ABC is still a gate for both

GLM's `.mmp` is generated by a hand-written XML adapter from per-voice SMFs;
the ABC→MIDI→`.mmp` product bridge is still a qualification item. Ardour's
new generator is also fixture-specific with an explicit timing manifest, not a
general ABC importer. The fair-comparison correction (both need a generation
adapter) therefore still applies; neither side has a production ABC→project
adapter.

## 3. Ardour claims superseded by the new receipt

The proposal's Ardour row/§1 still says “session reopen receipt missing” and
“distinct gmsynth programs/banks unproven.” The new receipt closes the
reopen/edit gates and the **program** part:

- save → instrument → patch tempo/range → **reopen** → render; reopen log
  reports `Flute`, `Bass`, `Piano`, `tracks=3`.
- v1→v2 edit applied to a copy of the same project and re-rendered.
- program changes 73/33/0 at tick 0; a controlled 73→0 swap on the same Flute
  notes changes the rendered peak/RMS/spectral centroid.
- The bank part (distinct SF2 banks) remains unproven; program changes are not
  bank changes.

Ardour still does **not** have: a general generator for arbitrary ABC/timing,
raw/GUI/batch stems, source-built/macOS receipts, or license clearance.
Those remain gates. LMMS still has: simpler project construction, native
`rendertracks`, fast cold start, and official macOS arm64 builds as
page-evidence. LMMS-first remains a defensible **preference**, not a decisive
production-quality advantage; the comparison is closer after this probe, and
the selection should stay provisional pending root review.

## 4. Recommendation to the conductor

1. Update the proposal's Ardour row: reopen/edit and distinct **programs** are
   now receipted; keep banks, general generator, raw/GUI/batch stems, macOS and
   licensing as open.
2. Qualify LMMS's “shared piano instrument” as two matched tracks unless a
   single-instrument routing receipt is added.
3. Qualify “complete PROJECT→MIX+STEMS” with the render-pad, master-taper and
   non-sample-sum facts; cite Ardour's 1-LSB reconstruction as the
   complementary receipt.
4. Do not call either side's generator “general” yet. Both need an explicit
   adapter contract; Ardour's is now demonstrably reopenable/editable on the
   shared fixture, LMMS's remains hand-written XML.
